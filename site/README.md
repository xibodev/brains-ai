# Brains website

The public Brains site is served by GitHub Pages at
<https://xibodev.github.io/brains-ai/>. It is plain HTML, CSS and a small optional
JavaScript bookmark migration. There is no framework, package installation, runtime
dependency or build step. Source lives in `site/` on `main`; open `site/index.html`
from the repository root for a local preview. GitHub Pages uses the GitHub Actions
source and deploys this directory without changing the public URL.

## Page structure

- Product: `index.html`, a short introduction, first-use example and latest release summary.
- Docs: `docs.html`, with `quickstart.html`, `connecting.html` and `coordination.html`.
- Reference: `reference.html`, with `cli.html` and `mcp.html`.
- Operations: `operations.html`, including trust, upgrades, services and recovery.
- Releases: `releases.html`, containing the six-entry generated recent history.

Shared assets are `assets/site.css`, `assets/site.js` and `assets/favicon.svg`.
Keep the white/slate, teal and blue identity. Navigation, documentation and release
content are present in the initial HTML and work without JavaScript. Repeat the same
header/footer when editing a page; do not replace them with runtime includes.

## Release synchronization contract

Maintain the site and release automation together on `main`. Site changes deploy
through `site-deploy.yml`; release synchronization commits only generated page
facts to `main` and explicitly deploys its artifact in the same run. See the
[maintenance/operations documentation](https://github.com/xibodev/brains-ai/blob/main/docs/OPERATIONS.md),
[release conditions](https://github.com/xibodev/brains-ai/blob/main/docs/QUALITY_GATES.md#recurring-release-conditions)
and [automation workflows](https://github.com/xibodev/brains-ai/tree/main/.github/workflows).

The directory sync allowlist is `index.html`, `quickstart.html`, `mcp.html` and
`releases.html`. Preserve paired `<!-- brains:NAME:start -->` and
`<!-- brains:NAME:end -->` comments exactly. Generated contents are overwritten.

- `release-version`: current visible version text, only in allowlisted files; at most four pairs per file when used. Currently used in Quickstart.
- `mcp-count`: visible core-tool count, only in allowlisted files; at most four pairs per file when used. Currently used on Product and MCP.
- `release-summary`: exactly one pair, in `index.html` only. Latest version, publication date, first two bounded highlights and a link to its release-page anchor.
- `release-history`: exactly one pair across the site, in `releases.html` only. Do not put release history back on the homepage.

The history retains `.release-entry`, `.release-meta`, `.release-details`,
`.release-badge`, `.release-link` and `release-vX-Y-Z` IDs. It is static HTML derived
from published GitHub release notes, not fetched by the browser. Layout styles stay
outside generated regions. Historical notes and version-qualified source URLs are
not current-version fields and must not be blindly rewritten.

The full MCP inventory is editorial HTML, not generated by the count marker. When
the supported surface changes, compare every `.inventory code` entry to the release
tag's `CORE_MCP_TOOLS`, then update explanations and links. A count-only update does
not establish that the inventory is current.

## Content authority

Use the published release tag, not unreleased main-branch features, for behavior:

- Audience and product boundary: `docs/product/PRODUCT_BRIEF.md`.
- Workflows: `docs/GUIDE.md`; verify literal command syntax in `src/brains/cli/app.py`.
- MCP inventory: `CORE_MCP_TOOLS` in `src/brains/capabilities.py`; parameter contracts in `src/brains/mcp/tools.py` and `docs/MCP.md`.
- Service, authentication and recovery: `docs/OPERATIONS.md` and `SECURITY.md`.
- Structure and contribution: `docs/ARCHITECTURE.md` and `CONTRIBUTING.md`.

The initial restructure is bounded to release tag `v1.5.0`. Its guide has known
syntax drift: task claims take `--code` and `--session`; Workspace claims use
`--minutes`; backup paths are positional; `upgrade` is for editable Git installs.
The tagged operations/source default MCP port is `9877`, not the guide's `8788`.
The MCP prose also lists tools absent from the core allowlist; the website inventory
follows the allowlist. Knowledge and checkpoint examples use MCP because the tagged
CLI does not register the commands suggested by the prose guide. Do not copy these
discrepancies back into website examples.
No site example represents actual command output or host readiness.

## Search and metadata

Each page needs one H1, a unique descriptive title and description, an absolute
canonical URL, matching Open Graph URL/title/description, and a Twitter summary
card. Keep titles/descriptions free of volatile release counts or versions.
Interior JSON-LD uses WebPage or TechArticle plus the visible breadcrumb hierarchy;
the homepage uses WebSite and SoftwareApplication. Do not invent ratings, authors,
dates, offers or rich-result promises. No image is required for these summary cards.

Keep `sitemap.xml` aligned with the ten canonical URLs, using the trailing-slash
project root for the homepage. Omit `lastmod` unless a meaningful source can maintain
it. A project-path `robots.txt` cannot govern the origin: crawl directives belong at
`https://xibodev.github.io/robots.txt` and require separate owner coordination.
Search Console verification and sitemap submission also require the site owner's
access; sitemap and schema markup do not guarantee indexing or a rich result.

## Verification

Run static and browser checks through the parent project's disposable Docker QA,
not against a host Brains service, database or native service manager. Verify:

- All ten pages parse, links and local fragments resolve, metadata/JSON-LD parse and sitemap URLs match canonicals.
- Exactly one H1 per page; breadcrumbs, primary/current navigation and sidebar hierarchy agree.
- Desktop and narrow mobile layouts, keyboard skip link, visible focus, no horizontal body overflow and readable code scrolling.
- Navigation, tool inventory and six release entries remain readable with JavaScript disabled.
- MCP inventory equals the published tag's allowlist; release history stays identical to the incumbent generated region until synchronization intentionally updates it.
- Release renderer is idempotent across the directory contract, without modifying metadata, canonical URLs, source pins or unrelated pages.

Legacy homepage sections retain `why`, `install`, `concepts`, `cli`, `mcp`, `console`,
`governance`, `operations`, `workflow`, `releases` and `docs`. Old tab hashes and
`index.html#release-vX-Y-Z` redirect through `assets/site.js`; ordinary section links
and the Releases navigation remain the no-JavaScript fallback. Test both initial
hash loads and hash changes within an already open homepage.
