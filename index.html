One control plane for
your AI coding agents

Brains is an operator control plane for directing, observing, and governing AI coding agents. Shared Workspaces, durable tasks and handoffs, local mailboxes, reusable knowledge, human approvals, and an inspectable audit trail — all on your machine, over SQLite.

The problem

Agents are isolated. Your work isn't.

Every AI coding tool runs its own process, its own session history, and its own partial view. Without a control plane, coordination becomes informal, state fragments across tools, and safety claims rest on conventions nobody can inspect.

🧭

Shared coordination

Workspaces, Sessions, tasks, claims, and handoffs with stable meanings — so two agents can share ownership without collisions.

brains-ai task-claim
📬

Durable local mailbox

Agent-to-agent mail that survives restarts. The durable store is authoritative; a live wake is best-effort and never loses mail.

brains-ai mailbox inbox
🧠

Reusable knowledge

Record a caveat, workaround, or decision once. The next session reads it instead of re-deriving it.

brains_knowledge_search
⚖️

Human authority

Asks and approvals are visible, attributable, and fail closed where the contract requires a human decision.

brains-ai decision-resolve
🔗

Reversible wiring

Connect supported harnesses over MCP. Brains preserves unrelated settings when wiring or unwiring your tools.

brains-ai wire / unwire
🔒

Inspectable evidence

A hash-chained audit log, governed-action records, and backup/restore contracts you can verify rather than trust.

brains-ai audit-verify

Operating model

Nine words that mean one thing each

Brains' value comes from stable vocabulary. Every surface — CLI, MCP, and browser — uses the same nouns.

TermMeaning
WorkspaceA repository or working directory used as the coordination scope. Sessions, claims, knowledge, and visibility all hang off it.
SessionOne durable coordination handle for an agent in a Workspace. Leases, checkpoints, and events preserve continuity across restarts.
TaskA unit of durable work with a code, status, and priority. Created, claimed, completed, released, or handed off.
ClaimExclusive ownership of a Workspace or task for a bounded period, so two agents cannot silently edit the same thing.
HandoffThe context you leave behind when you stop: what changed, what's next, what's blocking.
CheckpointA resume cairn dropped at a natural breakpoint so a fresh session can pick up without replaying a transcript.
Ask / ApprovalA human question or decision. Governed effects fail closed where the contract requires a person.
KnowledgeA recorded caveat, resolution, or environment note, scoped and searchable, so findings are not re-derived.
MailboxA durable local address for an agent Session. History is authoritative; wakeups are best-effort.

wire a harness

brains-ai wire

# or one, on an explicit transport

# inspect without changing anything
brains-ai wire --status

# remove Brains wiring; preserves unrelated settings
brains-ai unwire --tool codex
~/.claude.json — written by `brains-ai wire`
{
  "mcpServers": {
    "brains": {
      "type": "http",
      "url": "http://127.0.0.1:9877/mcp",
      "headers": { "Authorization": "Bearer <key>" },
      "_brains_managed": true
    }
  }
}
Adds the managed entry and preserves unrelated settings.
~/.codex/config.toml — sentinel-delimited block
# >>> brains managed >>>
[mcp_servers.brains]
url = "http://127.0.0.1:9877/mcp"
bearer_token_env_var = "BRAINS_MCP_BEARER_TOKEN"
# <<< brains managed <<<

The token is referenced by environment variable,
never written into the file.

Human authority

Governed effects, not good intentions

Review asks and approvals, inspect governed-action records, and verify the audit trail. Brains records decisions and results for actions routed through its governance controls.

  • Hash-chained audit log — audit-verify recomputes the chain and reports the first divergence, including truncation
  • Governed actions — actor, target, tool, argument digest, tier, decision, and result, linked to their audit entries
  • Argument digests, not arguments — the record proves what ran without storing payloads
  • Separation of duty — a Session cannot resolve the approval it requested
  • Owner-only secrets — managed binding files use POSIX owner-only modes or a verified Windows DACL

Trust note: Brains coordinates trusted local agents; its governance controls are not a process or network security sandbox. See Security.

verify the chain
$ brains-ai audit-verify
{
  "ok": true,
  "entries": 1284,
  "head_appended": 1284
}

# On tamper, ok is false and the response names the
# diverging entry id, the reason, and expected vs actual
# hash — so you can point at the row.
Operations

Recoverable by contract

SQLite is the supported source of truth. Backup, restore, readiness, and rollback have explicit contracts rather than best-effort behaviour.

💾

Backup & restore

Online backup to a .tar.gz with a manifest. Restore records its attempt before it touches anything.

brains-ai backup
🩺

Readiness

Truthful posture for database, migrations, listeners, and state directory — not a static green light.

brains-ai readiness
↩️

Recovery drills

Exercise the declared recovery policy against synthetic state before you need it.

brains-ai recovery-drill
🧱

Migration contract

Ordered, checksummed migrations with a frozen baseline. Unordered or altered migrations are rejected.

brains-ai upgrade
🧪

Isolated validation

Tests that can touch a service, database, or listener run in disposable containers, never against your install.

run_quality_gates.py
🖥️

Service definitions

Renderers for Task Scheduler, launchd, and systemd-user. Opt-in — see the note below.

brains-ai wire --status
▲

Background service is opt-in. Configure Task Scheduler, launchd, or systemd-user according to your OS configuration. After upgrading on Windows, reinstall the existing task with brains-ai service install to refresh its state-directory binding and runner; preserve any custom label and port options, then check brains-ai service status. A native manager cycle does not establish login or reboot persistence. Follow the setup guidance in Operations.

Workflow

One agent implements. Another reviews.

Use a shared Workspace to coordinate a task across two coding agents and continue where you left off.

1. Connect the tools

Register your repository as a Workspace and connect both coding tools to Brains over MCP.

2. Implement and review

Have one agent claim and implement the task. Ask the second agent to review the changes and report its findings.

3. Resolve questions

Exchange questions and findings through local agent mailboxes. File an ask when a decision needs your input.

4. Leave a handoff

Record what changed, what remains, and any blockers. The next session reads the handoff and continues the work.

peer review: inspect, then accept the exact request
# Requester: file for one peer with a five-minute open lifetime.
brains-ai help-file --subject "Review the migration" --question "Are existing rows preserved?" --from-session <requester-id> --to-session <peer-id> --timeout-ms 300000

# Peer: wait for help, then use the returned code instead of HR-example.
brains-ai inbox-wait --session <peer-id>
brains-ai help-get HR-example --session <peer-id>
brains-ai help-claim-code HR-example --session <peer-id>

# After review: supply the actual findings and supporting evidence.
brains-ai help-answer HR-example --session <peer-id> --answer <findings> --evidence <evidence>

help-claim-code accepts only the supplied request; it never substitutes queued work or launches a worker. A same-owner retry does not extend the claim. inbox-wait only waits for claimable peer help, not durable mail, and does not accept work. Read mail separately through mailbox inbox with the required Session attachment and binding proof. See the two-agent guide for ownership, targeting, and timeout rules.

v1.5.0

Sep 8, 2026Latest release
  • Exact peer-help acceptance: claim_help_request and the brains-ai help-claim-code CLI accept one specified request with atomic ownership checks. Same-owner retries return the existing claim without renewing its deadline or accepting different work.
  • Windows background services bind BRAINS_STATE_DIR before importing Brains and use task-owned supervisor recovery. Stop ends the runner before owned-child cleanup, with native qualification checking that the service stays stopped through the recovery window.
  • Safer macOS service cleanup verifies process identity before signalling and handles PID reuse without stopping an unrelated process. Uncertain identity or changed PID records fail closed rather than being discarded.
  • Native service lifecycle qualification covers Windows, macOS, and Linux manager cycles and cleanup for the release candidate. Publication remains human-approved and tied to the qualified source commit; manager-cycle evidence is not a claim of login or reboot persistence.
